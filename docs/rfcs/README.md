# RFC

RFC（Request for Comments）用于讨论尚未冻结、影响较大且存在真实替代方案的产品或技术设计。它保存问题、证据、备选方案和验证方法，不承担当前实现状态。

## 与其它文档的关系

```text
product.md
  产品目标与用户价值

architecture.md + Accepted ADR
  当前有效的长期架构约束

RFC
  尚需验证或选择的专项设计空间

roadmap.md
  能力依赖与演进顺序

Issue / PR
  当前执行规格、短期状态和交付证据
```

RFC 不能覆盖 Accepted ADR。研究结果如果改变了已接受的长期架构，应先通过新的 ADR 或明确的 supersede 关系更新架构权威。

## 状态

- `Draft`：研究仍在补充；
- `In Review`：证据、方案与待决问题足够完整，可以评审；
- `Accepted`：核心方向被接受，但不等于所有可选增强都成为承诺；
- `Rejected`：当前不采用，保留研究记录；
- `Superseded`：被后续 RFC 或 ADR 替代。

## 内容要求

专项 RFC 通常覆盖：

1. 问题与用户价值；
2. 目标与非目标；
3. 当前约束；
4. 方案与替代方案；
5. ownership 与数据流；
6. 失败语义和安全边界；
7. prior art 与证据；
8. 性能、可靠性、许可证和运维影响；
9. 验证方法与成功标准；
10. 未决问题。

RFC 应优先使用中文。代码符号、协议字段、标准专名和第三方项目名保留原文。

## 维护原则

RFC 记录仍有研究价值的设计空间，不写负责人、短期排期、分支状态或某次 PR 的实现过程。已经被代码和长期文档吸收的细节可以收敛为更短的当前研究结论，避免形成第二份实现说明书。
